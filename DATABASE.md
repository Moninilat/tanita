# Database design

This document describes the implemented V1 database schema for the Tanita tracker. The authoritative implementation is the initial Supabase migration at supabase/migrations/001_initial_schema.sql.

## Implemented V1 schema

The current schema contains three core tables:

- profiles
- locations
- measurements

This is the working database design for the release candidate V1. Derived metrics are calculated in application code and are deliberately not stored as raw columns in the measurement table.

## Table overview

### profiles

Each profile represents a person whose measurements are tracked.

| Column | Type | Notes |
| --- | --- | --- |
| id | uuid | primary key, generated by gen_random_uuid() |
| name | text | required, cannot be blank after trimming |
| birth_date | date | optional |
| height_cm | numeric(6,2) | optional, must be positive if present |
| created_at | timestamptz | default now() |
| updated_at | timestamptz | default now(), maintained by trigger |

### locations

Each location is a reusable place where measurements occur.

| Column | Type | Notes |
| --- | --- | --- |
| id | uuid | primary key, generated by gen_random_uuid() |
| name | text | required, cannot be blank after trimming |
| created_at | timestamptz | default now() |
| updated_at | timestamptz | default now(), maintained by trigger |

### measurements

One measurement row is one observation recorded at a specific date/time, for a specific profile and location.

| Column | Type | Notes |
| --- | --- | --- |
| id | uuid | primary key, generated by gen_random_uuid() |
| profile_id | uuid | required foreign key to profiles.id |
| location_id | uuid | required foreign key to locations.id |
| measured_at | timestamptz | required |
| entry_method | text | required; allowed values are manual and import |
| notes | text | optional |
| weight_kg | numeric(7,3) | optional, positive if present |
| bmr_kcal | numeric(7,2) | optional, positive if present |
| bone_mass_kg | numeric(6,3) | optional, positive if present |
| visceral_fat_rating | numeric(5,2) | optional, valid range 1 to 59 if present |
| body_fat_pct | numeric(5,2) | optional, range 0 to 100 if present |
| muscle_mass_kg | numeric(7,3) | optional, positive if present |
| muscle_quality_score | smallint | optional, positive if present |
| physique_rating | smallint | optional, positive if present |
| body_water_pct | numeric(5,2) | optional, range 0 to 100 if present |
| heart_rate_bpm | integer | optional, positive if present |
| metabolic_age | integer | optional, positive if present |
| abdomen_cm | numeric(6,2) | optional, positive if present |
| flexed_arm_cm | numeric(6,2) | optional, positive if present |
| arm_cm | numeric(6,2) | optional, positive if present |
| waist_cm | numeric(6,2) | optional, positive if present |
| hip_cm | numeric(6,2) | optional, positive if present |
| thigh_cm | numeric(6,2) | optional, positive if present |
| created_at | timestamptz | default now() |
| updated_at | timestamptz | default now(), maintained by trigger |

## Implemented constraints

### Required columns and not-null rules

The initial schema does not require all body metrics to be present. A measurement may be partial.

The required fields are:

- profiles.name
- locations.name
- measurements.profile_id
- measurements.location_id
- measurements.measured_at
- measurements.entry_method

All system timestamps are required.

### Row validation

The migration includes positive-value validation for applicable numeric fields and bounded ranges for percentage metrics:

- height_cm IS NULL OR height_cm > 0
- weight_kg IS NULL OR weight_kg > 0
- bmr_kcal IS NULL OR bmr_kcal > 0
- bone_mass_kg IS NULL OR bone_mass_kg > 0
- muscle_mass_kg IS NULL OR muscle_mass_kg > 0
- muscle_quality_score IS NULL OR muscle_quality_score > 0
- physique_rating IS NULL OR physique_rating > 0
- heart_rate_bpm IS NULL OR heart_rate_bpm > 0
- metabolic_age IS NULL OR metabolic_age > 0
- abdomen_cm IS NULL OR abdomen_cm > 0
- flexed_arm_cm IS NULL OR flexed_arm_cm > 0
- arm_cm IS NULL OR arm_cm > 0
- waist_cm IS NULL OR waist_cm > 0
- hip_cm IS NULL OR hip_cm > 0
- thigh_cm IS NULL OR thigh_cm > 0
- body_fat_pct IS NULL OR body_fat_pct BETWEEN 0 AND 100
- body_water_pct IS NULL OR body_water_pct BETWEEN 0 AND 100
- visceral_fat_rating IS NULL OR visceral_fat_rating BETWEEN 1 AND 59

The schema rejects blank or whitespace-only names using checks such as btrim(name) <> ''.

## Implemented foreign keys and delete behavior

The migration uses foreign keys with ON DELETE RESTRICT:

- measurements.profile_id references profiles.id
- measurements.location_id references locations.id

This means a profile or location cannot be deleted while measurement rows still reference it. This preserves historical integrity.

## Implemented entry method rules

The entry_method column is constrained to these values:

- manual
- import

This is intentionally a database check, not a free-form text value. The system UI should still map friendly labels like Manual to the persisted value manual.

## Implemented index set

The initial migration creates the following indexes:

- unique case-insensitive index on locations (lower(trim(name)))
- profile chronology index: measurements(profile_id, measured_at, id)
- location chronology index: measurements(location_id, measured_at, id)

These support ordered history queries and historical calculations by profile or location.

## Trigger behavior

The migration defines a single PostgreSQL trigger function:

- set_updated_at()

It is attached to:

- profiles
- locations
- measurements

Before each update, it sets updated_at = now(). This keeps the last modified timestamp automatic without relying on application-side writes alone.

## Explicitly excluded from the V1 schema

The initial schema does not include direct columns for:

- body_fat_mass_kg
- waist_to_hip_ratio
- bmi
- change_from_first_measurement
- change_from_previous_measurement

These are derived values and must be calculated from raw observations.

## Future schema decisions

These are not implemented in the current V1 migration and should remain documented as future decisions:

- RLS ownership and access model
- optional device metadata tracking
- segmental Tanita metrics
- historical height snapshots
- future entry methods beyond manual and import
- any additional metadata that becomes necessary for broader multi-user authorization or device management

## Current status

The initial schema is already deployed and working in Supabase. Documentation should treat it as the current implementation, not as a proposed design waiting for migration.

## Source of truth

When in doubt, treat the migration file as the authoritative operational schema. The documentation reflects the working model, and future schema changes must be introduced with a new migration rather than modifying an already-applied migration.
